# Saved catalog read performance — 2026-10-20

## Scope and status

This is a local candidate and measurement report. No remote D1 reads, provider
requests, migrations, deployments or commits were performed for this work.

- Candidate migration: `docs/proposals/0009_public_catalog_read_indexes.sql`.
- Index tests: `tests/catalog-read-indexes-20261020.test.cjs`.
- Browser change: the metadata-loading helper in `public/index.html`.
- Browser tests: `tests/catalog-filter-metadata-reuse-20261020.test.cjs`.
- No repository SQL query, old migration, price, status or observation logic changed.

The candidate adds seven non-unique indexes. It is outside automatic Wrangler
migration directories. Live database index definitions must be checked by the
operator before applying it; measurements used the checked-in `0004` schema.

## What caused the work

`D1ReadRepository.listCatalog` orders by `last_seen_at DESC, listing_id ASC`.
The original catalog index begins with platform, state and auction date, so it
does not supply this ordering. Original plans scanned listings, joined their
sources and used a temporary B-tree to order the result.

Discovery coverage is read once per public request, but its query filters by
`operation='discovery'` without a matching original index. That scans the
history receipts in the same table as the few discovery scopes.

Filter metadata reads thirteen fields from every matching listing and deduplicates
them in JavaScript. The saved-D1 route ignores `make`, while the browser previously
fetched a separate `/api/filters?make=...` response for each make change. The
existing HTTP cache intentionally treats these URLs as different keys.

## Candidate indexes

| Index purpose | Keys or predicate |
|---|---|
| Global listing order | `last_seen_at DESC, listing_id ASC` |
| Platform listing order | `platform, last_seen_at DESC, listing_id ASC` |
| Timed listing order | Global order, `WHERE is_timed=1` |
| Platform Timed order | Platform order, `WHERE is_timed=1` |
| Buy Now listing order | Global order, `WHERE buy_now_usd>0` |
| Existing normalized make filter | `upper(trim(make)), last_seen_at DESC, listing_id ASC` |
| Discovery coverage | `operation, platform, provider` |

The two Timed indexes are necessary companions to the general ordering indexes.
An intermediate recent-only experiment made an empty Timed query scan the entire
catalog. A platform query also needs its own partial index to avoid the same
problem within that platform.

The platform + Buy Now query retains the original selective
`idx_listings_buy_now` index and sorts its small matching subset. An additional
platform Buy Now index was not selected in the tested plans and was removed.

Fuel expression indexes improved a sparse global EV query but could make the
common gasoline/body query slower, and the platform fuel index was not selected.
These experiments were removed. Existing electric predicates and query planner
behavior are unchanged by application code.

## Correctness and measurements

Runtime: Node `v24.21.0`, SQLite `3.53.4`, Windows, SQLite databases in memory.
Initial investigation also used the saved 2,097-row public baseline and expanded
copies with unchanged dates/statuses. The candidate tests use reproducible
synthetic data at 5,000 and 10,000 listings plus one history receipt per listing.

Twenty-two list query shapes are generated by the actual repository implementation;
the coverage query mirrors the repository SQL.
Before and after the migration, tests compare hashes of the exact ordered rows,
including every selected field. Cases include:

- Global/platform lists, make aliases and missing makes.
- Current, Timed, Buy Now and EV categories, with platform variants.
- Failed-source exclusions, ended/unknown statuses, old observations and
  date-only schedules.
- Zero and missing prices, bounds, null fields and body/fuel groups.
- Matching/missing literal searches, cursor pages and discovery coverage.

The migration is also applied twice to prove idempotence; all public row hashes
remain unchanged. Empty Timed and electric queries retain the same results.
Timed plan assertions require the selective indexes. Timings are evidence,
not fragile test pass/fail thresholds.

The following run used five alternating before/after rounds, each taking the
median of nine warm executions. These are local CPU timings in milliseconds;
they do not measure D1 network latency or billable rows.

There is a real tradeoff for substring searches returning no rows: `instr(...)`
cannot seek a B-tree index, and scanning the recency index plus table rows can
cost more than a sequential table scan. Sparse EV filters can also inspect many
rows. This candidate does not claim zero timing regression for every query.
No planner hints or application query changes were made to hide that tradeoff.

Repeating the sensitive cases in a separate nine-round alternating check gave
10,000-row Timed/platform `0.375 → 0.345 ms`, platform Buy Now
`0.575 → 0.587 ms`, EV `16.745 → 7.318 ms`, platform EV
`9.867 → 8.600 ms`, and missing substring `10.728 → 10.900 ms`.
Timing variation reinforces the need to read the plans and the full-scan
limitation together with the elapsed times.

## Write and storage cost

The fixture measures 500 updates of last-seen, summary time, bid and update time,
then rolls back every value. In the latest run:

| Rows in fixture | 500 updates before → after | Allocated database bytes before → after |
|---|---:|---:|
| 5,000 | 2.818 → 9.396 ms | 6,119,424 → 7,135,232 |
| 10,000 | 3.272 → 10.869 ms | 12,083,200 → 14,106,624 |

An earlier isolated run measured `2.395 → 5.709 ms` for the 10,000-row fixture.
Index maintenance is an added write cost, not a free optimization. The allocation
increase was stable at 2,023,424 bytes (about 1.93 MiB) for 10,000 synthetic rows.

An update changing `last_seen_at` affects three new unconditional listing indexes
(global, platform and make); a Timed listing additionally belongs to two new
partial indexes, and a Buy Now listing to one. Discovery/history receipt inserts
add one entry to the coverage index. A receipt update changing only dates/status
does not change that index's key. These counts describe index entries, not
measured D1 billing.

## Browser metadata reuse

The helper reuses a response only when all these existing response fields confirm
saved public data: `ok === true`, `meta.read_source === 'd1'`,
`meta.known_rows_only === true`, and object-shaped `data`.

Reuse lasts at most 30 seconds from request start, stays in page memory and does
not extend on a hit. Models are filtered locally for the currently selected make.
Only concurrent requests for the same make share an unconfirmed request.
Provider responses remain specific to their make. Errors, malformed responses,
clock rollback and response-order races do not retain or restore an invalid
cache entry. Existing UI request/make guards remain.

The ten new browser tests plus related filter/product/pagination suites passed
49/49. The final combined run below passed 20/20:

```powershell
node --test tests/catalog-read-indexes-20261020.test.cjs tests/catalog-filter-metadata-reuse-20261020.test.cjs tests/stored-catalog-read.test.cjs
```

## Separate findings not implemented

- One SQL metadata aggregation could reduce D1-to-worker result size while still
  scanning the matching rows once. It would require an application query change.
- Exact detail lookup ORs `upper(vin_normalized)`, `upper(lot)` and
  `upper(source_listing_id)`. All three matching expression indexes are needed
  for an indexed OR plan; adding only two still scanned the fixture. This would
  add three more maintained indexes and is outside the current candidate.
